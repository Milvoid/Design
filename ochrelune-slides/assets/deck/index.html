低效作业识别系统

帮超算运维找出申请多、用得少的作业，并给出可以核查的依据

队长：詹承烨（上海交通大学安泰经济与管理学院）
开场一句话：这是一个帮超算运维找出低效作业的智能体。

申请多、用得少的作业，正在悄悄占住整台节点

以合成作业 #420077 为例：申请 64 核，两小时内平均只用 0.99 核

问题出在哪里

超算按申请量分配资源。作业一旦申请了 64 核，这 64 个核在它运行期间就不能分给别人，哪怕程序实际只用到了一个核。排队的用户看到的是“资源已满”，而节点上大部分核其实空着。

为什么现在很难发现

  • 数据分散：申请记录在 Slurm 里，实际用量在监控曲线里，运维要在两个系统之间来回比对。
  • 数量太多：同一批就有 160 项作业，逐项打开监控查看，一个值班员一上午也查不完。
  • 原因不一：有的是没开多线程，有的是在等 I/O，判断需要看完整段曲线，不能只看一个时刻。
先讲个例的反差，再按三下讲为什么人工很难发现。

系统怎么工作

五步找出该先检查的作业，处置决定留给运维

系统只读取数据、给出判断和建议，不直接改动任何作业

读取记录从 Slurm 读申请核数、GPU、内存和时长，从监控读同时段曲线。
→
检查用量先确认监控够不够完整，再判断低用量是否持续，归入五类低效之一。
→
估算闲置按有效观测时段，把闲置核数乘以时长累加成核时、卡时。
→
起草建议模型引用具体指标起草排查建议，例如用 1、2、4 核对比试跑。
→
运维确认按闲置量排序成清单；暂停等操作必须由运维核查影响、写明理由后确认。

一次运行交给运维的是什么

一张按闲置量排序的清单。每项作业点开能看到用量曲线、低效类型与依据、闲置核时和排查建议；系统不会自己暂停或修改作业。

判断依据分三层，避免把正常作业误报成低效

每一条判断都能回到原始记录和监控曲线

数据够不够

采样点少于观测窗口的一半、或正处在启动预热期的作业，先标为“数据不足”，不参与低效判断，并提示补齐监控。

例：一项作业只有 18 个采样点、窗口要求 61 个，结论写“数据不足”。

低得够不够久

只有低用量持续覆盖大部分观测时段才判为低效。短暂的空闲（例如读写数据的几分钟）不算，避免把正常的阶段性波动当成浪费。

例：#420077 在两小时里没有一段用量超过 2 核。

浪费有多大

按有效观测时段估算闲置核时和卡时，清单按浪费量从大到小排序，运维从最值得处理的作业看起。

例：#420077 约 126 核时，排在清单第一位。
